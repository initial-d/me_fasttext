我的评价是：这轮更新值得认真测试，尤其是长任务和多轮编码；决定要不要切换主力模型时，最有用的指标是“完成一个合格任务要多久、花多少钱”。单看输出速度，很容易把模型、缓存和工具环境的收益混在一起。

这里补一个偏推理系统的视角。我没有完成 1017 版的成套对照评测，因此下面是评估方法和官方部署说明的解读，不是亲测排行榜。

1．先把“快”拆开，否则大家可能在比较不同的东西

首个 token 的等待时间、持续输出速度、完成整个任务的时间，是三个指标。长上下文请求第一次发过去，可能主要在等 prefill；连续修改同一个仓库时，前缀缓存可能省掉大量重复计算；工具循环里，测试、检索和人工纠错又可能占掉大部分时间。

DeepSeek 10 月 20 日的官方部署文章，明确把 Vision Encoder、Prefill、Decode 分开部署，并讨论了跨请求的 KVCache 复用。这说明用户体感里的“快”，包含整套服务系统的贡献。

同一套任务，至少应记录：输入长度、缓存命中与未命中的输入 token、输出 token、工具调用次数、首 token 延迟、最终完成时间。比较 API 和本地部署，还要说明硬件、并发和版本。

2．编码能力，最好用“可验收的改动”来测

挑 10～20 个自己真的会做的小任务：修一个 bug、补一个边界条件、修改接口、读一段陌生代码、完成一个跨文件功能。两边从同一个提交开始，用同样的需求、权限和工具，提前写好验收条件。

重点看首次通过率、失败后能否正确定位、有没有破坏原有行为，以及需要多少人工纠正。跑多次，并保留失败案例。一个模型输出更多代码或跑更多测试，都不能自动说明任务完成得更好。

成本也应按任务算：总账单 / 验收通过的任务数。把失败重试和人工接管计进去，才接近实际选择。

3．缓存命中 token 与新计算 token，不能当成同一种工作量

长任务不断重发历史上下文，累计输入 token 可以很大；其中一部分如果命中缓存，计算开销与全新输入不同。把所有 token 加起来再除价格，可以描述这次账单，却不适合据此推出“模型算力便宜多少倍”。

同样，官方的集群吞吐和每卡收入，属于特定流量与部署条件下的数据。个人单卡、第三方 API、不同缓存策略，需要各自的测量。

4．一个值得研究的小切口：静态记忆的存储效率

KVCache 保存的是上下文计算产生的状态；Engram 式 n-gram 表保存的是训练得到的可查询参数。两者都涉及存储与访问，但身份、生命周期和正确性条件不同。

对于冻结的记忆表，可以独立研究：保持原始 hash ID、head 布局和 dtype，压缩存储之后按原 ID gather。这让存储优化有了清晰的验证边界：无损模式逐行比对原始字节，再检验模块输出；近似模式则需要额外测完整模型的质量。

我维护的 me_fasttext 正在做这个切口，已有 C 行存储和 PyTorch 适配器。当前验证覆盖官方 Engram 小型模块接口，float32、float16、bfloat16 的完整模块输出一致；没有验证 1017 的真实权重、GPU 调度或端到端质量，不能把它写成新模型已经获得的收益。

项目与验证入口：https://github.com/initial-d/me_fasttext/blob/5c5ce139049cfbed47dfa36a5eca69acd3cf648e/docs/engram_quickstart.md

我的判断是，这轮模型讨论最值得留下的是可复现的“任务质量—时间—成本”记录。对用户，它帮助决定是否切换；对开发者，它帮助区分下一步该优化模型、缓存还是数据访问。
