我认为 DeepInfer 这次开源最有价值的地方，是把“模型能跑”到“服务跑得划算”之间的一部分工程细节公开了。研究者可以沿着请求、调度、计算和存储这条路径，分析端到端成本，而不只是看一个算子快了多少。

不过，官方文章也明确说明，KVCache 管理和负载均衡组件由于与内部基础设施耦合较深，目前尚未完整开源。因此，拿到仓库之后，仍需要核对自己的部署条件和缺失组件。

下面讲三个我觉得值得深入的技术点，来源是 10 月 20 日的官方部署文章；我没有复现其生产集群吞吐。

1．Prefill 和 Decode 分开，优化目标才能分开

Prefill 处理新输入，Decode 逐步生成。二者的计算、访存和并发特征不同，使用同一种资源配比，容易出现一边排队、另一边空转。

官方方案分别控制首 token 延迟和生成间隔，并用负载均衡、专家并行和异步调度提高有效吞吐。对使用者最关键的是：吞吐曲线要和延迟约束一起看。增加 batch 能提高总吞吐，同时也可能增加单请求等待；不能拿不同延迟目标下的峰值做比较。

2．KVCache 复用，本质上是一次“读缓存还是重算”的决策

官方把分页 Block KVCache 放到独立 3FS 存储集群，把 SWA KVCache 留在产生它的机器内存中。这样做的理由涉及不同状态的复用时长、容量和读取成本，并非所有缓存都适合统一落盘。

缓存命中也有开销：匹配、从存储读取、传到 HBM。只有这些开销小于被省掉的重算，复用才真正有利。官方讨论了异步取 KV、逐层传输与前向计算重叠，正是在处理这一点。

因此，评估缓存压缩最好同时报告：总容量、命中率、实际读取字节、解码 CPU 时间、传输时间，以及首 token 的 p50/p95。文件变小只是其中一项。

3．读放大，是压缩存储里容易被忽略的一笔账

举个说明机制的假设例子：每行 128 个 float32，行宽是 512 字节；64 行组成一个解压块。只请求一行，也可能需要解压 32 KiB，这时解压字节量是返回字节量的 64 倍。

这个比例不是 DeepInfer 的测量值。实际代价还取决于请求是否集中、同批能否合并、缓存是否命中、压缩率和解码速度。同批多个 ID 落在同一块，按块合并后只解一次，就能降低重复工作；随机访问分散到许多块，则可能削弱压缩收益。

这也是我在做 Engram 式静态记忆存储时坚持保留的指标：压缩率与 gather 延迟放在一起，报告块读取、解压次数和尾延迟。

这里要区分两类数据：KVCache 是请求上下文状态；冻结的 n-gram embedding 表是模型参数。静态表可以先做离线布局和无损编码，再保留原 ID 查询；KVCache 需要处理生成、复用、版本和生命周期，不能直接照搬静态表假设。

我维护的 me_fasttext 提供一个可复现的小切口：C ABI 接收原始全局行 ID，返回原始顺序的字节；调用方负责 dtype、形状和 head 偏移。上层可以通过 PyTorch 适配器接到 gather 位置。当前是不可变 CPU 表、每 worker 独立句柄，不具备 DeepInfer 的 GPU/RDMA 调度能力。

我们在 9 张真实训练的英文字符 n-gram SGNS 表上，按相同训练更新签名组织数据，原生无损 XOR 文件节省约 6.9%～9.1%；对应实验的暖查询 p50 比同布局普通压缩增加约 1.5%～3.7%。文件计算包含头、全量行映射、块描述和 payload，排除了键索引与模型其他部分。

这些数字是小型字符 n-gram 实验，不是真实 Engram 权重，也不是相对常驻 tensor 或 raw mmap 的速度结论。它说明如何把存储收益与查询代价一起验证，不能外推成 DeepInfer 已经获得的改进。

对开源社区，我觉得最好的参与方式是做一个边界清楚的贡献：固定权重、硬件和请求负载，提交可运行对照，把压缩收益、数据移动成本和输出质量放在同一份报告中。这样的结果，无论更快还是更慢，都能帮助下一位开发者选择。
