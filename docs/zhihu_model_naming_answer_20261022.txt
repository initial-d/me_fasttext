从普通用户角度看，这个名字确实偏长；从做部署和实验的角度看，带日期的版本名有用。不过，再清楚的名字也只能是入口，真正支撑复现的是可定位的模型快照。

题目里的“最差名称排行榜”，我把它理解为一场关于可读性的讨论，不据此判断模型能力，也不推断厂商内部的版本管理规则。

我会把一个模型的身份分成三层：

第一层是展示名，让用户认得出来。

第二层是调用标识，让程序知道请求哪个服务。调用标识有可能是可变别名，是否固定到某个快照，需要服务方说明。

第三层是实际构件：权重修订、tokenizer、模板、推理实现和配置。做技术对照，需要记录这一层。

为什么第三层这么重要？假设两个人都说“我用的是 V4.1 Flash”，但一个测试缓存未命中的首轮长输入，另一个测试高命中的连续编码；一个使用不同模板或量化导出，另一个使用另一套推测解码配置。两人的速度、账单和输出可能不同，这时仅靠名字，无法解释差异。

比较合理的发布方式是“短展示名 + 明确更新记录 + 不可变快照标识”。普通用户看短名，工程师能展开看到构件与兼容性。日期能帮助定位，但 MMDD 单独使用会有跨年歧义，完整日期和仓库 revision 更可靠。

这里还有一个和模型压缩有关的细节：同一组源权重，经过不同导出方式，也不一定是同一个数值模型。

如果导出只是改变布局、做无损编码，应该能够还原原始字节。若做量化、近似向量合并，导出的值已经改变，应记录算法、阈值、源文件哈希与重建哈希。不能只给它们起同一个模型名，再把“跑出来差不多”叫作无损。

以我维护的 me_fasttext 为例，我们正在研究冻结 n-gram 记忆表的存储：原始 ID 可以通过映射保留，但原始 ID 相同，并不意味着值完全相同。无损模式要逐行字节一致；近似模式会单独写出 APPROXIMATION.json，记录阈值、dtype、源与重建哈希，并直接检查每行到最终代表向量的误差，避免多次合并带来的漂移。

这类实验也说明“99% 相似”不能直接写成“只有 1% 损失”。余弦相似度描述方向，范数描述长度。即使范数相同，余弦为 0.99，对应的相对 L2 差异也是 sqrt(2-2×0.99)，约 14.1%。完整模型质量还要另外测。

所以，对技术回答、论文和部署记录，我建议至少保留以下信息：模型来源与不可变 revision；tokenizer 和模板版本；导出/量化/压缩配置；推理代码提交；硬件和请求参数；缓存状态；质量与速度的原始结果。

这比争论应该叫“4.1.1”还是“1017”更能解决实际问题：别人能否找到同一份东西，复现同一类请求，解释同一份结果。
