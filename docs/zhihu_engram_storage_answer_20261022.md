# Engram 的 DRAM 与压缩成本：知乎回答

对应问题：https://www.zhihu.com/question/2087854646002037757

---

把已经训练好的表从 HBM 搬到 DRAM，本身只是改变参数放在哪里。只要取出的每一行数值、row ID、多头偏移和 dtype 都一致，后续计算拿到的输入就一致。它因此可以不改变模型函数，但系统成本仍然存在。

我想补充存储层的角度。这里至少要区分三件事：

1. 参数搬家。表仍是原来的表，容量没有变，只是从显存转移到主机内存。精度转换、改变寻址、漏取行都属于额外变化，不能归入“只搬家”。

2. 无损编码。表在文件中用更少字节表示，查询时恢复原始字节。模型不用重新训练；代价转移到解码、映射表、缓存和 I/O。文件更小也不自动意味着 RSS 更低，操作系统页缓存和解码缓存都要实测。

3. 近似合并或量化。恢复的向量发生变化，需要用完整模型做任务评估。“相似度 99%”不能直接等同于“能力损失 1%”。

为什么预取有机会隐藏成本？因为 n-gram 的查询地址可以从 token ID 算出，可以提前安排读取和传输。但如果预取开始后，到使用时只剩很短的计算窗口，数据仍可能来不及到；突发请求、缓存未命中、并发排队也会影响尾延迟。

评估时，可以先用一个简单账本：每 token 未命中缓存、必须传输的向量行数 × 每行维度 × 每个数值的字节数，再乘 token 吞吐量，估算传输需求。还要计入重复 ID 去重、批量访问、多层多头、实际总线带宽和调度。压缩块另有读放大：只要一行，也可能要解压整个块。把一个模型的特定配置测量当成所有机器的结果，会漏掉这些条件。

我维护的 me_fasttext 正在研究其中的无损存储和查询接口。已经实现了独立 C 批量取行后端，通过 PyTorch CPU 适配器接到 Engram 演示模块。固定版本的微型接口检查覆盖 float32、float16、bfloat16，以及 Python/native/native-XOR 三条路径，原始行字节和下游门控、ShortConv 输出一致。这只验证接口，还没有真实 Engram 训练权重或 GPU 运行结果。

压缩实验用的是公开英文文本训练的字符 n-gram SGNS，不是 Engram 哈希桶。最高 4/8/12 阶、三个种子共 9 张表，按相同训练更新分组做自适应 XOR，实际文件节省约 6.9–9.1%，已计入文件头、行映射和块描述；不含键索引和模型其余参数。原来的每一位都恢复，但与相同布局的普通编码相比，这组热查询的 p50 增加约 1.5–3.7%。分组还需要训练签名，收益不能直接套到 Engram。

另一个近似实验同时要求余弦和模长比 ≥0.99，12 阶向量存储缩小约 2.15 倍。词的 n-gram 均值分量平均相对 L2 变化约 0.48%，但单行平均约 4.2%、最大约 14.2%。后者必须作为向量近似来评估，不能宣传成无损或完整模型能力只损失 0.48%。

因此，对“免费吗”的回答是：容量和计算可以重新分配，但 DRAM 容量、读取带宽、CPU 解码、CPU→GPU 传输和预取调度仍要付账。真正有价值的比较应在相同硬件、批大小和质量目标下，报告总文件、RSS、冷/热 p50/p95、吞吐及完整模型任务结果。问题标题中的具体参数量，我这里没有做对应模型的核验，不将它作为这些实验的前提。
