我认为 Engram 很值得关注的一个亮点，是把“什么时候知道要读什么”变成了架构设计的一部分。这为存储优化留下了一个清楚的接口。

先把机制说准：Engram 的表项是训练得到的向量，经过投影、门控和局部卷积融入主干。它不是把“某句话的正确答案”直接存进一个可读的知识库。查表地址确定，也不意味着生成答案一定正确。

https://arxiv.org/abs/2601.07372
https://github.com/deepseek-ai/Engram

通常 MoE 要先算出当前层 hidden state，再由 router 决定激活哪些专家。Engram 的 n-gram 查询 ID 可以从已有 token ID 计算，因此有机会在这些向量真正被使用之前安排读取。prefill 的输入已知，适合成批处理；自回归 decode 时，未来尚未生成的 token 仍然未知，不能把“可提前寻址”理解成整段未来输出都能预取。

接下来可以把系统拆成两部分：模型决定查哪些原始行、如何用这些向量；存储后端决定这些行如何编码、排列、读取和恢复。固定 tokenizer、哈希设置、多头偏移、dtype 和行字节，就可以单独比较存储实现。

举个简单例子：模型请求行 [7, 3, 7]。文件内部可以重排这些行，也可以只保存一份字节完全相同的行，但后端必须按原 ID 返回 [原行7, 原行3, 原行7]。原 ID→物理位置的映射、重复访问的语义和错误处理，都是接口的一部分。这样压缩不会悄悄改变哈希冲突或头布局。

这也解释了为什么 C 接口可以服务 PyTorch 模型：C 负责批量 gather，Python 适配器负责把 ID、buffer、dtype 和 shape 接起来，再交给原来的投影和门控。接入点是一层冻结的向量表。给任意现成 Transformer 新增 Engram 模块，则涉及训练或适配，不能靠一个存储库自动完成。

我维护的 me_fasttext 正在做这个接口。已有 C 行存储和 PyTorch CPU 适配器，在固定版本的 Engram 微型演示中，float32/float16/bfloat16 × Python/native/native-XOR 共九种组合，取行字节和下游模块输出一致。这是接口验证；还没有真实 Engram 权重、GPU 调度或完整语言模型任务结果。

另一个值得研究的问题是：高阶 n-gram 会不会提供更多压缩机会？字符 n-gram 经常共同参与一个词的训练更新，某些前后缀确实可能形成相近向量。可是“共同更新”不保证最终相同：初始化、出现频率、碰撞和其他更新都会影响结果。应测真实训练表里的分布，不能预设所有前后缀都达到 99% 相似度。

仓库目前的参考实验使用公开英文文本训练的字符 SGNS：最高4/8/12阶、三个随机种子，128维。同更新分组的自适应 XOR 无损文件节省约6.9%、8.9%、9.0%；文件头、行映射和块描述已计入，键索引及模型其余参数未计入。随机打乱布局时，XOR 没有带来同样收益。这说明这组实验存在可利用的局部性，也说明布局条件很重要。

这些是字符 n-gram 结果。Engram 的 token n-gram 会映射到哈希桶，一个桶可能承受多种模式的更新；字符前后缀关系和训练签名不能直接移植过去。4/8/12阶的趋势同样不能证明阶数无限增加就更有效。

如果要往这个方向做下一篇工作，我会固定一个完整模型和真实记忆表，先保留寻址与行字节，比较 resident tensor、raw mmap、无损分块编码；再独立加入近似策略。报告文件体积、构建峰值、RSS、冷/热p50/p95、完整任务质量及高频/低频查询切片。容量收益和访问代价一起看，才知道这条新稀疏维度能走多远。
